VCS • 01 Git Branching Strategy (GitFlow vs Trunk-Based)
Page 1 of 5
✗ BEFORE : AD-HOC / FRAGILE WORKFLOW
"git me code kaise manage kare sab log direct main branch pe push kr rhe h"
Workflow Bottleneck / Risk: Uncontrolled Main Branch: Direct pushes to main without feature branching or PR reviews cause merge collisions, broken builds, and untracked code regressions.
✓ AFTER : STRUCTURED ENTERPRISE RELEASE WORKFLOW
Establish an enterprise Git branching model for the CareConnect EHR engineering team: 1. Core Protected Branches: - 'main': Production-ready, locked branch requiring signed releases and green CI builds. - 'develop': Integration branch for testing completed features. 2. Supporting Branches: - 'feature/-': Branched off develop, merged via Pull Request. - 'bugfix/' & 'hotfix/': For urgent production patches directly into main and develop. 3. Branch Protection Rules: Require at least 1 peer code review approval, passing automated CI checks, and disable direct pushes or force pushes to main.
Governance & Stability Gains: Enforces a structured GitFlow strategy with protected branches, mandatory PR reviews, and eliminates risk of main branch breakage.

VCS • 02 Conventional Commits & Semantic History
Page 2 of 5
✗ BEFORE : AD-HOC / FRAGILE WORKFLOW
"git commit me kuch bhi likh dete h jaise 'fixed code' ya 'update'"
Workflow Bottleneck / Risk: Opaque Commit History: Meaningless commit messages make debugging git bisect impossible, obscure code intent, and prevent automated changelog generation.
✓ AFTER : STRUCTURED ENTERPRISE RELEASE WORKFLOW
Enforce the Conventional Commits specification (v1.0.0) across the CareConnect repository: 1. Commit Message Standard: '(): ' - Types: feat (new feature), fix (bug fix), chore (tooling/deps), refactor (no logic change), test (unit/e2e tests), docs. - Example: 'feat(cpoe): add LOINC catalog selector and STAT urgency triage' 2. Atomic Commits: Each commit must represent a single logical change with working tests. 3. Pre-Commit Verification: Configure Husky git hooks to validate commit message format before allowing the commit to be recorded.
Governance & Stability Gains: Creates an audit-ready commit history adhering to Conventional Commits standards, enabling automated versioning and changelogs.

VCS • 03 CI/CD Pipeline & Automated Quality Gate
Page 3 of 5
✗ BEFORE : AD-HOC / FRAGILE WORKFLOW
"code push hone par manual build chalao aur dekho chal rha h ya nahi"
Workflow Bottleneck / Risk: Manual Build Vulnerability: Manual verification allows broken dependencies, failing tests, or unlinted code to slip into production unmonitored.
✓ AFTER : STRUCTURED ENTERPRISE RELEASE WORKFLOW
Engineer an automated GitHub Actions CI pipeline (.github/workflows/main.yml) quality gate: 1. Trigger Criteria: Automatically trigger on every push and pull request to 'main' and 'develop'. 2. Build & Test Matrix: - Backend: Set up JDK 21, run 'mvn clean verify', execute unit tests, and check test coverage. - Frontend: Set up Node.js 20, run linting, and compile Angular production build with 'npm run build'. 3. Gate Enforcement: Block PR merges if any test fails, lint checks error out, or the build fails. 4. Build Artifacts: Cache Maven dependencies and Node modules to optimize pipeline execution speed.
Governance & Stability Gains: Establishes a zero-touch automated CI gate validating builds, tests, and code quality on every PR before merge.

VCS • 04 Semantic Versioning & Release Tagging Workflow
Page 4 of 5
✗ BEFORE : AD-HOC / FRAGILE WORKFLOW
"release ka version kaise de v1 v2 kuch bhi daal de kya"
Workflow Bottleneck / Risk: Arbitrary Versioning: Random version numbers break dependency compatibility, violate SemVer standards, and confuse stakeholders during deployment rollbacks.
✓ AFTER : STRUCTURED ENTERPRISE RELEASE WORKFLOW
Implement Semantic Versioning (SemVer 2.0.0: MAJOR.MINOR.PATCH) and Release Tagging: 1. Increment Criteria: - MAJOR (e.g. 2.0.0): Breaking API contract changes or database schema incompatibilities. - MINOR (e.g. 1.1.0): New backward-compatible clinical features (e.g. CPOE module added). - PATCH (e.g. 1.0.1): Backward-compatible hotfixes (e.g. BMI rounding bug fix). 2. Git Tagging: Create annotated cryptographic tags (e.g., 'git tag -a v1.0.0 -m "Release 1.0.0"'). 3. Automated Release Notes: Automatically generate release changelogs grouped by Features and Bug Fixes from Conventional Commits.
Governance & Stability Gains: Standardizes versioning with SemVer 2.0.0, transparent git release tags, and automated changelog generation.

VCS • 05 Production Deployment & Rollback Strategy
Page 5 of 5
✗ BEFORE : AD-HOC / FRAGILE WORKFLOW
"production me deploy krte waqt kuch fat jaye to dubara manually theek karo"
Workflow Bottleneck / Risk: Downtime & High Risk: Lack of an automated rollback mechanism causes extended system downtime and potential healthcare data corruption during broken deploys.
✓ AFTER : STRUCTURED ENTERPRISE RELEASE WORKFLOW
Architect a zero-downtime Release Deployment and Automated Rollback strategy: 1. Frontend Deployment (Netlify): Atomic deploys with instant rollback capability to the previous successful deploy hash if smoke tests fail. 2. Backend Deployment (Docker Container): Use immutable image tags (e.g., 'careconnect-backend:v1.0.0') rather than mutable 'latest' tags. 3. Health Check & Verification: Automated post-deployment smoke test pinging '/api/actuator/health' before routing live traffic. 4. Disaster Recovery: Document 1-click rollback procedures to revert DNS or containers to the prior verified stable version.
Governance & Stability Gains: Ensures zero-downtime releases with immutable Docker container tags, automated health checks, and instant 1-click rollback.
